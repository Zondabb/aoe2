# 城墙建成后的卡顿

## 卡顿的原因

城墙由许多 1 格大小的墙体实体组成：一圈基地周界约 200～280 块，AI 防守默认预算为 384 个墙体或城门实体，上限 512。修复前，有几段代码的开销与“墙块数 × 实体数”成正比，建好城墙后每帧都要承担。

`tests/benchmark_walls.gd` 在默认地图上为 AI 方（封建时代）放置完整周界（216 个实体，含 4 座城门），30 个村民在墙内外采集，游戏 2 倍速，按 60 FPS 固定帧长运行 900 帧。带计时的副本测得，城墙带来的额外开销主要是：

| 来源 | 每帧平均 |
| --- | ---: |
| 墙体外观 `FortificationVisual._wall_shape` | 13.6 ms，同一批放下的墙在同一帧刷新时形成 100 ms 以上的单帧尖峰 |
| 村民在墙边移动（碰撞避让查询到大量墙体，导航每帧检查所有建筑） | 约 4.5 ms |
| 迷雾重建（每块墙都是视野源） | 约 2 ms |
| 小地图 | 约 1 ms |
| 城门开关触发导航静态索引全量重建 | 平均不到 1 ms，但每次 26～31 ms 的单帧尖峰 |

AI 决策 tick 也会变重：中期局面加上 280 块墙后，每次 tick 从约 132 ms 增至约 200 ms，观测从 118 KB 增至 290 KB，因为每块墙都按完整建筑序列化。

本次修复了墙体外观和城门开关两项；其余几项见文末。

## 实现方式

### 墙体外观

每块墙每 0.25 秒（模拟时间）刷新一次外观，根据相邻墙体选择端柱、转角或某个方向的直墙。原实现每次都遍历实体容器的全部子节点（默认地图约 1300 个，大部分是树）寻找相邻墙体。

现在同一帧内所有墙体共用一份邻居快照：第一次查询时遍历一次容器，把建筑按位置写入 4 × 4 模拟单位的空间桶；放置预览（幽灵）会随鼠标移动，单独放在一个短列表里，每次查询都按当前位置判断。每块墙只检查自身周围 2.6 格内的桶——一格相邻加上城门 1.5 格的门柱偏移，已覆盖所有可能相连的位置。是否相连的判断（同队、未删除、预览规则、城门门柱换算、方向去重）与原实现逐行相同，并在查询时用当前状态判断。

同一帧内新增或释放子节点会改变子节点数，快照随之重建；待删除、队伍变化、预览确认等都在查询时判断。真实建筑不会在帧内移动，若被移动，下一帧的快照会反映新位置。0.25 秒的刷新周期和其余外观逻辑未改变。

### 城门开关

自动城门由附近友军打开、无人时关闭。开关只改变城门自身的碰撞尺寸；它的导航尺寸（路线规划用）在自动、常开状态下始终为零，导航网格不变。原实现每次开关都排队重建导航服务的静态碰撞索引：重新收集约 1400 个障碍物、生成导航标记并比较，再整体重建碰撞空间桶。

现在城门在导航尺寸不变时调用 `NavServiceHolder.update_static_entity(gate)`，只替换这座城门在碰撞空间桶中的记录，并更新其变化检测签名。城门未被跟踪、索引待重建或已离开场景时，仍回退到原来的全量重建。锁闭、解锁等改变导航尺寸的操作，以及首次更新，也仍走全量重建。碰撞避让对静态障碍物只做“是否相撞”的判断，桶内顺序不影响结果。

## 测量与复现

```powershell
godot --headless --fixed-fps 60 --path . --script res://tests/benchmark_walls.gd -- --scenario none
godot --headless --fixed-fps 60 --path . --script res://tests/benchmark_walls.gd -- --scenario walls
godot --headless --fixed-fps 60 --path . --script res://tests/benchmark_walls.gd -- --scenario build
godot --headless --path . --script res://tests/run_wall_shape_index.gd
godot --headless --path . --script res://tests/run_gate_static_index.gd
```

`--fixed-fps 60` 使每帧推进相同的模拟时间，帧的实际耗时即 CPU 开销。`none` 为无城墙，`walls` 为完整周界，`build` 为同一周界由 10 个村民施工。

以下数据来自云端 Linux 容器（2 vCPU，Godot 4.7.2 headless）。修复前后的项目交替运行，有城墙的两个场景各两轮取平均，最大值取两轮中较大者；绝对耗时随机器变化，应在同一台机器上比较。

| 场景 | 修复前平均 | 修复后平均 | 修复前 P95 | 修复后 P95 | 修复前最大 | 修复后最大 | 超过 33 ms 的帧（900 帧中） |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 无城墙（一轮） | 8.6 ms | 8.5 ms | 17.5 ms | 17.2 ms | 27.6 ms | 28.0 ms | 0 → 0 |
| 完整周界 | 30.6 ms | 17.7 ms | 128.0 ms | 39.0 ms | 182.3 ms | 67.0 ms | 178、186 → 84、93 |
| 周界施工中 | 27.6 ms | 15.2 ms | 124.7 ms | 34.3 ms | 177.4 ms | 60.9 ms | 140、141 → 42、63 |

两个版本的模拟行为一致：完整周界场景中城门都开关了 16 次，施工场景都完成了 39 块墙。带计时的副本中，墙体外观（`FortificationVisual._process`）每帧开销从 13.5～14.1 ms 降至 1.1 ms；修复前采样期间有 16 次导航静态索引重建（两次测量中单次最长 26～31 ms），修复后为 0 次。

`run_wall_shape_index` 随机生成直线、斜线、含城门墙段和约 900 个密集散布的墙体与城门，覆盖两队相邻、地基、放置预览，以及同一帧内移动预览、确认预览、改变队伍、待删除、释放和新增墙体等情况，共逐块比较 12,628 次，结果与原全表扫描完全一致，覆盖端柱和四种直墙方向。人为把查询范围缩到 1.2 格、跳过预览列表、或快照不随子节点数重建时，该测试分别报告 11、53、263 处不一致。

`run_gate_static_index` 在默认地图上放置完整周界，让 4 个村民分别穿过四座城门往返，共 24 次开关。每次开关后的碰撞索引都与全量重建结果逐条一致，期间没有发生全量重建，导航网格不变；手动切换常开、自动后城门分别离开和回到索引，锁闭时仍排队全量重建。修复前的代码在此测试中有 4 项失败；人为让关门时不写回记录后，测试报告 8 帧索引不一致且关闭的城门不再阻挡。

`tests/` 下原有的 90 个 `run_*` 测试在修复前后各运行一次：70 个两边都通过；18 个两边都失败，且退出码、失败数和错误信息完全相同（多为需要外部 AI 服务或联机的测试，以及 `run_tests`、`run_original_art_scale`、`run_town_center_occlusion` 等原有失败）；没有结果不同的测试。

## 剩余开销

修复后完整周界场景仍比无城墙多约 9 ms 每帧，900 帧中约 90 帧超过 33 ms。带计时的副本中，主要差别为（括号内为无城墙时）：

| 来源 | 每帧平均 |
| --- | ---: |
| 迷雾 `fog_of_war_holder` | 7.1 ms（5.1 ms），单次重建最长 34 ms |
| 单位物理更新 | 5.5 ms（0.9 ms） |
| 小地图 | 3.4 ms（2.1 ms） |
| 墙体外观 | 1.1 ms（无） |

剩余的超长帧主要是迷雾重建尖峰与这些开销落在同一帧。可继续优化的方向：

- 墙边单位移动：墙体同时登记在视野空间索引和导航静态索引中，单位每次碰撞避让查询都会取到附近墙体；导航服务每帧检查所有建筑（含每块墙）的变化。
- 迷雾和小地图：每块墙都是视野源和小地图标记。
- 城门：每座城门每 0.15 秒仍遍历一次实体容器寻找附近友军（4 座城门合计每帧约 0.5 ms）。
- AI 观测：墙体原先按完整建筑序列化，现已改为只含位置、生命值、施工、通行和城门状态的精简记录，见 [AI 决策 tick 的主线程开销](ai_tick_performance.md#城墙与城门的精简记录)。
