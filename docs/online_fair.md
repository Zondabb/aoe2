# 联机对等调度与有限预测（协议 v6）

`online_fair` 保留玩家主机和轻量 Python 中转。主机决定有序输入，双方执行同一套固定步长游戏逻辑；云端不运行 Godot，不计算寻路、经济、战斗或 LLM。两位玩家都在本地显示预测反馈，预测不会进入游戏状态或校验摘要。

## 指令的生命周期

1. 玩家操作分配本队独立递增的 `seq`，记录当前输入帧 `source_tick` 和未来执行帧 `execute_tick`。共同输入窗口根据实测 RTT 自适应调整，按 3-tick 帧取整；2 倍速初始为 **150 ms（9 ticks）**，低延迟稳定后可降至 **100 ms（6 ticks）**。1 倍速最低为 200 ms（6 ticks）；高 RTT 时会加大窗口。两端使用相同规则，本地预测隐藏等待，实际生效仍有延迟。
2. 主机自己的操作也进入同一未来帧队列。非主机操作经 Python 转发到主机，服务根据连接注入 `team`。过期或超出容量的操作明确拒绝，不偷偷提前执行或只给客端改到更晚的帧。
3. 主机提前广播 `input_frame`，内容是待执行输入，不提前扣费、创建建筑或移动单位。双方竞争同一帧的操作按队伍交替排列；队内人工指令优先于 AI。每帧最多 62 条游戏操作。
4. 开局等待客端完成时钟校准并确认收到首批准备帧。之后主机连续发送 `input_frame` 和 `input_commit`，确定该帧在主机单调时钟中的执行时刻，**不再等待每帧 `input_ack` 往返**。累计接收确认仍保留用于观测，提交只需留出单程传输和调度余量。
5. 双方根据同一时间表，每次推进一个 `1/30` 秒固定步，在执行帧用同一游戏规则接受或拒绝指令。客户端未收到提交或尚未到执行时刻就等待。普通非法操作是失败的空操作，不触发整局回滚。
6. 主机执行完成后发送 `frame`：成功操作、摘要以及每条人工指令的 `{team, seq, accepted}` 结果。客端核对自己同帧的结果与摘要后确认，并消除或平滑修正本地预测。观众只重放这些完成帧。

AI 指令也走准备帧。模型过期、会话和重复 ID 在主机入队时检查；执行时使用双方相同的人工接管代次、托管切换代次与过期 tick，避免等待中的 AI 操作覆盖较新的手动指令。自然语言指令只在主机对应执行帧交给本队 AI，不广播文本。

## 时间线与恢复

`clock_probe` / `clock_reply` 经现有服务双向转发，不依赖两台电脑的系统时间相同。客户端从最近 8 个样本中选择低 RTT 样本估算时钟偏移并平滑调整；主机取最近样本的 RTT 75 分位，给提交留出半个 RTT 加 10 ms 的到达余量（最少 12 ms）。两端不再以“主机算完，客端才开始”为正常节奏。

时钟采样只在世界同步完成后启动，主机还需收到客端初始关键帧确认。捕获或恢复关键帧后丢弃旧探针和样本，并暂停探针收发 200 ms，避免加载期间积压的请求把 CPU 加载时间误算成网络 RTT。保留原有时钟偏移、已公布输入窗口和执行时刻；新的有效高 RTT 仍会正常扩大窗口。

输入窗口包含指令上传余量和提前准备所需的模拟步数。窗口变化通过 `input_commit.input_delay_ticks` 与 `delay_from_tick` 提前公布：`execute_tick = source_tick + delay_for_source(source_tick)`。从指定的未来 `source_tick` 开始双方一起换用新窗口，已经发出的输入继续使用旧规则。窗口增加会提前公告；缩短需连续两次检查稳定，且每次最多减少 3 ticks。准备端同时保护旧规则下尚在传输的输入和即将使用较短窗口的输入，避免提前封帧。关键帧包含 `fair.delay_schedule`，失步恢复后仍可正确解释旧输入。

准备窗口与共同输入窗口分开，给客端指令留出传输余量。网络拥塞、极端不对称链路或某台电脑过载仍可能造成暂时偏差和减速；这不是严格同时的硬实时协议，也不消除可信主机的作弊权限。常规同步用共同截止时间推进，主机仍保留约 0.6 秒已执行帧确认窗口作为失联保护。

状态摘要不一致时沿用低频全量关键帧恢复，清除所有本地预测，恢复人工接管代次，再重发尚未执行的准备帧和提交时刻。不存在逐输入保存整局历史、逆转碰撞或重放整个世界的预测回滚。自然胜负在双方相同的帧边界停止；测试工具通过未来帧的内部结束操作验证最终帧一致。

## 预测范围

| 操作 | 本地即时反馈 | 确认前不改变的状态 |
| --- | --- | --- |
| 移动、停止、编队 | 己方单位的绘制位置，鼠标选择和遮挡轮廓跟随 | 实体坐标、寻路、碰撞、命令 |
| 攻击、采集、施工 | 向已可见目标的有限接近表现 | 伤害、死亡、采集、施工进度 |
| 放置建筑或城墙 | 黄色待确认轮廓或虚线 | 权威实体、导航障碍、资源 |
| 训练、研究、城门切换、取消队列 | 建筑附近的待确认提示 | 正式队列、人口预留、资源、科技、城门导航 |

移动预测只检查已可见区域中的短路径，最长推进 0.45 秒、相对真实位置最多偏移 2 个世界单位。成功且路径一致的移动不拉回落后的真实坐标：显示保持前进，以真实推进量的 35% 逐渐消耗预测领先，待真实位置追上后交回常规插值。拒绝、路径变化或确认后持续停滞才平滑修正；旧指令的确认不会清掉同单位更新的预测。未确认提示最多保留 3 秒；死亡、断线、恢复和退出也会清理。攻击命中、资源扣除和迷雾不会预测，AI 只观察确定的游戏状态。

## 部署与服务开销

双方游戏和 Python 联机服务必须一起更新到 **v6**，v5 及更旧客户端不能混用。AI Python 服务的 HTTP 协议没有变化。

服务新增的工作是校验小消息、转发准备帧和时钟报文、保存最多 60 个未完成准备帧的摘要及少量提交时间信息。它不保存第二份游戏世界，不按模拟 tick 运行游戏，也不访问模型。消息数量会增加；默认每连接限流改为 `MESSAGES_PER_SECOND=300`、`MESSAGE_BURST=600`，以容纳高倍速的准备、提交和确认消息。若部署环境显式覆盖这些值，需要相应调整；这不是并发容量保证，仍应根据实际云主机压测。

```powershell
python -m pytest multiplayer_service_python/tests -q
Godot_console.exe --headless --path . --script res://tests/run_online_fair.gd
Godot_console.exe --headless --path . --script res://tests/run_prediction_reconciliation.gd
Godot_console.exe --headless --path . --script res://tests/run_incremental_transport.gd
Godot_console.exe --headless --path . --script res://tests/run_lockstep_state.gd
python tools/test_online_fair_e2e.py --godot "<Godot console executable>" --host-team 0
python tools/test_online_fair_e2e.py --godot "<Godot console executable>" --host-team 1
python tools/test_online_fair_e2e.py --godot "<Godot console executable>" --host-team 0 --delay-ms 0 --jitter-ms 0 --max-input-ms 250
python tools/test_online_fair_e2e.py --godot "<Godot console executable>" --host-team 1 --default-map --max-final-window-ms 450
```

E2E 启动真实服务、两个 Godot 玩家和晚加入观众。每个玩家连接经过独立 TCP 延迟代理，默认每方向增加 25 ms 与 0–10 ms 抖动，保持字节顺序。测试覆盖预测不修改完整状态、连续移动/停止、非法指令拒绝、同一目标帧生效、强制失步恢复、观战和最终摘要一致。额外用独立直线移动测量操作到首次显示移动、真实移动、指令确认的时间，并逐显示帧检查确认后的后退距离（默认上限 1 像素）。`--max-input-ms` 可限制真实移动开始的延迟；`--delay-ms 0 --jitter-ms 0` 运行本机低延迟场景。记录双方同一 tick 的墙钟完成时间并检查时间线偏差；JSON 保留原始曲线及 RTT、窗口策略变化。`--max-final-window-ms` 可检测默认地图加载或恢复是否误抬高最终输入窗口。测试数据与排行榜使用临时目录，不调用真实付费模型。

实现入口：`scripts/network/fair_lockstep.gd`、`scripts/network/client_prediction.gd`、`scripts/network/network_match.gd`、`scripts/network/network_session.gd`。

历史 v5（2026-11-12）验证：Python 联机服务 103 项通过；Godot 有限预测与调度 33 项、协议 46 项、状态恢复 130 项通过；真实延迟测试分别交换主机，常规帧完成时间差的 95 分位约 35–55 ms，最终双方与观众 tick 和摘要一致。这是同机多进程加人工延迟的回归结果，不代表公网或云端并发压测。


### v6 修复验证（2026-11-13）

Python 服务 116 项通过；Godot 调度与采样 61 项、协议 53 项、状态恢复 130 项、预测连续性 4007 项通过。最终四组真实服务/Godot 多进程测试均通过：

| 场景 | 主机到真实位移 ms | 客端到真实位移 ms | 同帧完成时间差 P95 ms | 确认后直线后退 px |
| --- | ---: | ---: | ---: | ---: |
| 低延迟，主机队伍0 | 96.7 | 96.2 | 6 | 0 |
| 低延迟，主机队伍1 | 95.2 | 97.7 | 6 | 0 |
| 25+0–10ms/方向，主机队伍0 | 296.4 | 303.4 | 33 | 0 |
| 25+0–10ms/方向，主机队伍1 | 330.4 | 303.1 | 28 | 0 |

以上使用 2 倍速；低延迟场景最终共享窗口为 100ms，人工延迟场景为 300ms。预测反馈测得约 6–18ms；这是 headless 进程的呈现坐标采样，不是显示器输入延迟测量。所有测试仅有主动注入的一次失步，恢复后双方与观众最终 tick、摘要一致。

额外默认大地图测试覆盖初始加载、晚加入观战和强制关键帧恢复：RTT 约 156–166ms，最终共同窗口保持 300ms，同帧完成时间差 P95 为 34ms，三方最终摘要一致。测试过程中发现并修复了加载耗时污染 RTT 的问题；初始同步前不采样，关键帧操作后隔离积压探针。

窗口长度是帧调度参数，操作发生的帧内时刻、寻路处理和负载仍会影响真实位移时间；这些同机人工网络结果不代表所有公网链路或云端并发性能。
