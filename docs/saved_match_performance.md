# 存档性能排查与帧率显示

排查对象：`存档 2026-10-11 17-31-10.json`。读取原文件后在 `.godot` 内复制一份进行测试，没有覆盖用户存档。

存档有 24 个单位（18 名村民）、32 座建筑、1070 个自然资源，以及双方合计 634 条迷雾记忆。单位模拟平均约 2 ms，寻路队列处理平均约 0.015 ms，队列最多 2 条。这份存档的主要瓶颈是静态资源、迷雾、小地图和遮挡轮廓的工作量，不能只归因于单位数量。

## 游戏内显示

右上角常显实测 FPS 和平均帧间隔，按 F3 展开/收起最近最大帧耗时、引擎帧/物理耗时、绘制调用、对象数量、模拟倍速和暂停状态。实测 FPS 使用真实时间，暂停和加速不会改变它的计量口径。显示每 0.5 秒刷新，详情展开时每秒统计对象，折叠时不扫描实体。

引擎 Performance 监控值可能延迟刷新，并包含渲染等待，应作为参考；不能把“引擎帧”与“物理”两项相加当作独立 CPU 总耗时。瓶颈定位使用组件调用的直接计时。[Godot Performance 文档](https://docs.godotengine.org/en/stable/classes/class_performance.html)

## 测量与有效改动

测试使用本机 NVIDIA GeForce RTX 2060、Godot 4.7.1、OpenGL Compatibility、1280×720、关闭垂直同步及限帧。每个场景重新读取同一存档并保留保存时的镜头和 0.45 倍缩放；预热 2 秒、采样 5 秒。组件计时固定每次推进一个 1/60 秒的模拟步，不能把组件平均值直接转换为实时 FPS。

初始完整场景平均帧间隔 22.6 ms（约 44 FPS），P95 为 48.4 ms。关闭迷雾更新后的平均帧间隔为 6.8 ms，关闭小地图更新后为 9.0 ms；这些是诊断对照，正式游戏保留这些功能。

保留的优化及直接计时结果：

- 小地图复用静态资源的标记、占地、可见性和投影多边形，位置、占地、阵营、迷雾版本及窗口变化仍会使缓存更新。单次标记刷新约 14.5 → 8.9 ms。
- UI 复用图标元数据和 AtlasTexture，避免选中单位后每帧重新读取 JSON、创建纹理。选中村民的信息面板刷新约 0.745 → 0.136 ms，文明和时代变化仍使用对应图像。
- AI 黑板复用当前对局的真实实体列表和静态可见性，排除迷雾记忆代理，并保留旧测试场景的通用路径。一次完整 AI 决策约 22.4 → 17.8 ms。
- 迷雾对至多 2×2 格的占地进行等价直接查询，并在同一次重建内复用刚检查过的静态几何，避免记忆和可见性阶段重复检查。可见性处理约 4.2 → 3.1 ms。

完整帧间隔两次最终测试分别为 19.4 ms 和 24.9 ms，P95 分别为 43.2 ms 和 55.6 ms。整体帧率仍有波动，没有足够证据宣称已稳定 60 FPS。迷雾完整刷新仍可能耗时约 16–20 ms，AI 也有周期性尖峰；大视野下遮挡轮廓会增加绘制工作。测试没有减少单位、资源、迷雾精度或改变更新间隔。

原始对比与两次最终测量保存在 [saved_match_performance_results.json](saved_match_performance_results.json)。

可加 `--scenario saved_camera --live-only` 只测原存档镜头的实际帧间隔；加 `--components-only` 只做组件和细分调用计时。输出位于 `.godot/saved-match-performance-<label>.json`。

验证包含 FPS 39 项及实际 GPU 渲染 40 项、AI 黑板缓存 62 项、小地图缓存 47 项、图标缓存 14 项、迷雾缓存/矩形独立对照 47 项；已有 HUD 278 项、小地图 49 项、GPU 小地图 13 项、AI 时代推进 767 项、自然侦察 11 项及存档核心 43 项检查均通过。

## 2026-11-01：大存档 5 FPS 排查

排查对象：`存档 2026-10-30 23-35-04.json`（第 1543 秒，2 倍速，外部 AI 服务）。91 个单位（64 名村民，正在伐木、交货，弓箭手在交战）、280 座建筑（其中 235 段木栅墙）、1070 个自然资源、2 片湖泊，双方迷雾记忆各约 340 条。

在 2 核云端虚拟机上 headless 读档（不含 GPU 绘制，只用于相对比较）：每秒约 3 帧，帧间隔中位数约 280 ms，物理步也跟不上（每秒约 24 步，对局只跑到设定速度的八成）。卡顿来自每步和每帧的 CPU 工作。逐函数计时找到的热点：

| 热点 | 原因 | 处理 |
| --- | --- | --- |
| 迷雾重建 | 每支箭进出实体容器都触发一次完整迷雾重建，并重扫 1640 个子节点、重算 1350 个静态占地；交战时一帧好几次 | 箭矢增删只更新缓存列表（与重扫结果顺序相同），不再触发重建 |
| 迷雾表现层 | 纹理、迷雾记忆、1354 个静态对象显隐随每次迷雾更新执行：2 倍速时每秒 20 次，帧率低时一帧还要追赶几次 | 视野栅格仍每 0.1 秒游戏时间更新；表现层最多每 0.09 秒真实时间一次，其余由 `_process` 补上最新状态。移动单位的显隐仍每步更新 |
| “某方能否看见某物”查询 | 小地图每次刷新约 1300 次、采集村民每步约 1100 次，都现场换算占地格 | 每个迷雾版本用 C++ 一次算出全部静态对象的可见位（`AoeSimKernel.fog_rects_seen`），查询直接读缓存；迷雾节点先于小地图处理 |
| 砍倒一棵树 | 每次触发完整导航重建，单次约 80～160 ms 卡顿：两片湖的岸线逐格做多边形测试（约 26 ms），清障层逐格填充，碰撞索引全部重建 | 岸线格子按湖泊和半径缓存；清障层由 C++ 填充（`nav_layer_border` / `nav_mark_rects`）；只是有障碍消失时，碰撞索引只删掉对应记录 |
| 建筑变化轮询 | 每个物理步给 280 座建筑生成签名数组 | 追赶时每帧一次，比较时不再分配数组 |
| 单位精灵 | 每步格式化动画名、查找子节点；追赶时同一帧重复绘制 | 动画名、解析结果和精灵节点缓存；一帧内的后续步只保留最后一次请求 |

结果（同一存档、同一台虚拟机，前后交替各跑两次，每次采样 15 秒）：

| 项目 | 修改前 | 修改后 |
| --- | --- | --- |
| 每秒帧数 | 3.2 | 20.7（其他时段多次测得 23～30） |
| 帧间隔中位数 | 281～297 ms | 38～41 ms |
| 物理步 | 每秒 23.7 步，对局只跑到设定速度的 79% | 每秒 30 步，满速 |
| 砍倒一棵树时的导航重建 | 80～130 ms | 20～35 ms |

联机锁步的模拟结果不变：`bench_lockstep_frame.gd` 整局状态哈希与修改前相同（原生和 GDScript 回退一致）。新的 C++ 函数与 GDScript 版逐位相同，`run_native_sim_equivalence.gd` 新增可见位和清障层对比，改错一处条件能被发现。全量测试结果与修改前相同。

仍然较重的部分：单位逻辑约 14 ms/步（每秒 30 步，约占一个核心的四成），迷雾记忆约 10 ms/次，小地图刷新约 6 ms/次，城镇中心射击的目标搜索每 0.25 秒扫描全部实体，235 段木栅墙每 0.25 秒游戏时间各自重算一次外形。`tests/benchmark_saved_match.gd` 现在也支持使用外部 AI 服务的存档。
