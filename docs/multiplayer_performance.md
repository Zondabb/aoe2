# 联机同步卡顿与断开排查

2026-10-27 在 `spectator` 分支检查“联机响应迟钝、不到半分钟自动结束”。默认 480 地图约有 1085 个同步实体，单份完整 JSON 快照约 195 KB。

## 已确认的问题

1. 网络发送间隔使用 `_process(delta)` 的模拟时间；默认游戏 2 倍速会把预期 10 Hz 的快照放大到约 18–20 Hz，心跳与超时也错误地随倍速变化。
2. 每份快照重复写入约一千个资源与地形实体。不在视野内的资源也被重新显示，然后被迷雾再次隐藏，导致缓存反复失效；墙门存在无状态变化时重建视觉的成本。
3. 接收循环逐份应用积压的完整世界，阻塞输入和下一帧。首份世界实例化时继续收到新快照，还会造成接收缓冲区或服务输出队列拥塞。

保留旧脚本进行 4 倍速压力对照，约 34.6 Hz、7.27 MB/s，客端首包应用约 292 ms。服务明确以 `slow_consumer` 关闭连接（WebSocket 1008），对手收到带该原因的 `match_ended`。这次不是 `rate_limited`。默认 2 倍速空局的 45 秒基线未复现断开，因此不能把用户每次断开都直接归为同一原因。

## 修复

- 网络发送、收包超时、心跳和命令计数窗口均使用真实单调时间；快照最多 10 Hz，不随模拟速度加倍，也不补发过时帧。
- 收包每帧有数量和时间预算；连续积压的完整快照只应用最新一份，保持控制消息与结束消息的顺序。
- 发送缓冲拥塞时跳过已过时的中间快照；接收缓冲有界地预留首包加载余量，单条消息大小限制保持不变。
- 不变的静态实体跳过重复写入；迷雾保持对资源可见性的所有权，墙门只在状态变化时重建。探索掩码缓存不变数据的验证结果，不跳过输入校验。
- 服务日志记录限流、慢消费者、超时的原因和队列指标，不记录昵称、命令内容或凭据。对手收到具体 `disconnect_reason`；客户端显示中文原因和可用的 WebSocket 关闭码。

## 本机验证

以下性能数据来自真实本机服务与 Godot headless 客户端，属于主循环测量，不代表带图形界面时的 GPU 帧率。发送量通过抽样快照大小估算。

| 条件 | 快照频率 | 估算发送量 | 客端平均帧耗时 | 结果 |
| --- | ---: | ---: | ---: | --- |
| 旧版，2 倍速 | 18.55 Hz | 3.62 MB/s | 23.14 ms | 45 秒完成，存在较高同步成本 |
| 修复后，2 倍速 | 9.54 Hz | 1.87 MB/s | 7.37 ms | 两玩家和观众稳定 45 秒 |
| 修复后，8 倍速 | 9.19 Hz | 1.80 MB/s | 27.38 ms | 两玩家和观众稳定 45 秒；模拟负载更高 |
| 修复后，2 倍速加 80 单位 | 9.35 Hz | 约 2.0 MB/s | 9.63 ms | 两玩家和观众稳定 45 秒 |

```powershell
python tools/test_network_stability.py --godot "<Godot console executable>" --duration 45 --speed 2 --spectator
python tools/test_network_stability.py --godot "<Godot console executable>" --duration 45 --speed 8 --spectator
python tools/test_network_stability.py --godot "<Godot console executable>" --duration 45 --speed 2 --extra-units 80 --spectator
```

测试使用临时本机服务与独立数据库，不调用模型。报告和日志在 `.godot/network-stability-*`。`--baseline` 只用于保留了修改前脚本私有副本的本机，不随仓库分发旧脚本。

如果更新客户端与服务并重启后仍出现断线，保留界面上的具体错误、对应客户端日志和服务日志。`slow_consumer` 是接收端积压，`rate_limited` 是发送量超出服务限制，`send_timeout` 是网络写入超时；三者不能混为一谈。
