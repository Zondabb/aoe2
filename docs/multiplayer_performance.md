# 联机同步性能

## 当前 v3：增量操作帧

主机不再每秒发送 10 份完整世界。每帧只有有序操作、tick 和 SHA-256 摘要；空帧仍推进模拟。双方每帧运行三个 `1/30` 秒固定步，步在物理帧中逐个执行；主机最多领先客端确认 6 帧，观众独立跟随。

本机三进程回归（默认地图，队伍 2 为主机，453 tick）中，客端收到 151 个操作帧，共 18,934 字节，平均约 **125 字节/帧**。按目标 10 帧/秒计，操作帧约 **1.3 KB/s**，另有 ACK、玩家输入、心跳及 WebSocket/TCP 开销。这里的操作负载较轻；大量选中单位、连续下令时会增加。

该次观众中途加入的完整关键帧约 **0.54 MB**，只发送一次。客端额外注入一次资源错误，收到第二个关键帧修复，之后重新稳定使用增量帧。三个进程最终 tick 与摘要一致。关键帧保存精确浮点位模式，防止跨 JSON 实现的微小舍入造成假失步。

降低网络流量不等于免除模拟成本：双方及每个观众都需要运行完整游戏逻辑，并生成校验摘要。帧以 6 帧窗口流水线推进，往返延迟加客端缓冲超过 0.6 秒才会降低游戏速度；没有客户端预测，客端操作的生效延迟约为往返延迟加 1–2 帧。寻路使用固定请求数量预算，不能因设备快慢而改变模拟顺序。

复现入口：

```powershell
python tools/test_incremental_e2e.py --godot "<Godot console executable>"
python tools/test_incremental_e2e.py --godot "<Godot console executable>" --default-map --host-team 1
Godot_console.exe --headless --path . --script res://tests/bench_lockstep_frame.gd -- 60 40
python tools/bench_lockstep_e2e.py --godot "<Godot console executable>" --army 30 --seconds 20
```

输出包含每个进程的 tick、摘要、操作帧流量、关键帧数量和失步次数；临时日志在 `.godot/incremental-e2e-*`。测试主动注入的那一次客端失步是预期行为，额外失步会使测试失败。

## 增量同步卡顿排查（signal_simple）

改为 v3 后联机明显卡顿，原因有四个，彼此叠加：

1. **串行确认屏障。** 主机必须等客端确认上一帧才开始下一帧，而客端收到帧才开始计算。每帧耗时 = 主机计算 + 中转 + 客端计算 + 中转，两台机器轮流空等。有往返延迟时更明显。
2. **集中执行。** 一个渲染帧里连续跑 3 步、全量校验和 3 次迷雾刷新，每 100 ms 卡一次；单位位置也只按 10 Hz 跳变，没有插值。
3. **每帧全量校验。** 每帧把整个模拟状态（含约 1000 棵树、路径、迷雾）转换成 Variant、排序字典、序列化成约 0.58 MB JSON 再做 SHA-256，耗时超过一个模拟步。
4. **每步固定开销。** 每步扫描所有约 1200 个实体子节点 4 次做编号和排序；迷雾的纹理、记忆和节点显隐（纯表现）每步刷新 3 次，单机只需 10 Hz。

对应修改：

- 帧流水线：主机按实际时间产出帧，按 tick 保存已发布摘要，确认异步到达，领先窗口 6 帧。客端缓存帧，1 帧抖动缓冲，积压时追赶。关键帧请求在帧边界回答。
- 每个物理帧执行 1 步（主机最多 2、客端追赶时最多 4），每渲染帧最多 2 × 速度 步。对局速度取主机的 `[game] speed` 并在帧内广播（v3 原实现按 1 倍实际时间推进，比单机默认 2 倍速慢一半）。
- 每帧摘要改为二进制紧凑摘要（`LockstepState.digest`）；每个整模拟秒的帧改用完整摘要（`LockstepState.full_digest`，见下节）。原 JSON 形式的 `checksum()` 保留给关键帧往返测试。
- 新增实体按 `child_entered_tree` 增量编号，单位/建筑/箭矢的 net_id 顺序缓存；迷雾每步只重建可见栅格，表现层在渲染帧按 10 Hz 刷新。
- 结果不变的热点优化：空间哈希对单位直接读取定点坐标、按 net_id 用原生整数排序；`units_in_radius` 使用类型化字段；路径点可见性检测内联定点运算（2 万条随机线段与原实现逐一比较一致，快 3.4 倍）。
- 中转服务：每处理一条消息让出一次事件循环，默认输出队列由 8 提高到 64。玩家对 30 个单位一次下令就是 30 条指令连续转给主机，旧设置下可能因 `slow_consumer` 断开主机。

下表为 1 倍速测量；2 倍速需要每秒 60 个模拟步，CPU 需求翻倍。同一 2 核虚拟机、两个客户端同机时，默认地图加每方 5 / 15 个士兵分别达到 1.35× / 1.17×（目标 2×），瓶颈是 CPU。

验证结果：同一场景下，修改前后跑 129 tick 的完整状态哈希完全一致（`bench_lockstep_frame.gd` 输出 `deep state`），说明模拟结果没有改变。下列数字来自 2 核云端 Linux 虚拟机，headless，主机、客端和中转同在一台机器，只用于相对比较。

单进程帧开销（默认地图，每方 60 个单位，`bench_lockstep_frame.gd -- 60 40`）：

| 项目 | 修改前 | 修改后 |
| --- | --- | --- |
| 每网络帧（3 步 + 校验） | 293–305 ms | 136 ms，另有约 12 ms 迷雾表现（渲染帧，10 Hz） |
| 单个模拟步 | 79 ms | 43 ms |
| 每帧校验 | 55 ms | 4.8 ms |

双进程实测（`bench_lockstep_e2e.py`，默认地图加每方 N 个士兵，采样 15 秒；速度 1.0 = 实时）：

| 场景 | 修改前 | 修改后 |
| --- | --- | --- |
| N=10，本机回环 | 0.30×，每帧 170–240 ms 卡顿 | 0.97×，99% 帧 ≤ 71 ms，最差约 110 ms |
| N=10，往返延迟 120 ms | 0.23×，卡顿 145–220 ms | 0.96×，99% 帧 ≤ 81 ms |
| N=5，往返延迟 120 ms + 0–80 ms 抖动 | — | 0.99×，客端仅 1% 物理帧等待 |
| N=30，本机回环 | 0.15×，卡顿 280–440 ms | 0.63×（两进程同机，CPU 已饱和） |

剩余主要开销是单位移动本身：局部避让、邻居查询和路径点可见性检测约占模拟步的七成，单机同样存在，联机时双方都要计算。机器跟不上实时时，对局会整体减速，而不是周期性冻结。

### 紧凑摘要与完整摘要

紧凑摘要只哈希主要玩法数值，护甲、建筑接收资源的设置、城门导航记录等隐藏字段不在其中。`tests/run_lockstep_digest.gd` 对默认地图上一个运动中的局面逐个修改 357 处同步状态，原 JSON 校验能发现其中 355 处，紧凑摘要漏掉 94 处。这类差异要等到影响某个被哈希的数值时才会暴露，可能已过去很久。

因此 `frame_checksum()` 按 tick 选择摘要：帧结束 tick 是 30 的倍数（每个整模拟秒，即每 10 个 3-tick 帧）时使用完整摘要，其余帧使用紧凑摘要。选择只取决于 tick，主机、客端、观众以及帧、确认和关键帧对同一 tick 总是用同一种摘要；任何隐藏状态的分歧最迟在 1 个模拟秒内被发现，随即用关键帧修复。

完整摘要覆盖 `capture()` 的全部状态，取值规则与之相同（引用转为网络 ID、字典按键排序、`Vector2` 分量不区分正负零），直接对二进制形式（`var_to_bytes`）做 SHA-256，不组装关键帧字典，也不生成 JSON。同一测试中，完整摘要对 357 处改动的判定与原 JSON 校验完全一致；人为让它保留 `Vector2` 零的符号、漏掉迷雾、漏掉地面支撑、把弱引用一律记为 0、不排序字典或少算一个字段时，测试分别报告分歧。

| 摘要 | 默认地图 | 27 分钟存档（1446 个同步实体） |
| --- | ---: | ---: |
| 原 JSON 校验 | 27 ms | 75～90 ms |
| 完整摘要 | 11 ms | 25～31 ms |
| 紧凑摘要 | 3 ms | 7～8 ms |

`bench_lockstep_frame.gd -- 60 60` 中每帧校验的中位数不变（约 4.3 ms），每 10 帧一次的完整摘要帧最长 24～28 ms，摊到每帧约 2 ms。

摘要的计算方式改变后，与之前的客户端即使协议版本相同也不能混用，否则会持续判定失步。

## 历史 v1 问题

旧版使用完整 JSON 快照，静态资源、实体和迷雾反复发送，默认场景约 195 KB/帧，正常 10 Hz 时约 1.87 MB/s。旧实现还曾按游戏倍速增加发送频率，引发收发队列积压；复现中的断开原因为 `slow_consumer`。后续 v1 修复将网络频率改为实际时间并合并过时快照。

v3 保留实际时间超时、消息大小限制和连接诊断，但不再合并增量帧。日志中的 `slow_consumer`、`rate_limited`、`send_timeout` 或 `idle_timeout` 分别对应输出积压、输入限流、发送超时与心跳超时。旧 `tools/test_network_stability.py` 和周期快照测试针对 v1，不能作为当前 v3 的性能断言。
