# 联机同步性能

当前 v8 使用 [对等调度与延后执行](online_fair.md)。下文 v3/v4 的带宽和性能数据保留为历史基线，不能用作新协议的输入延迟或总流量结论。

## v8 第二阶段优化（2026-11-17）

已实现三项：

- **玩家完成帧去重。** 客端不再重复收到 `move`、`attack`、`gather` 等已准备并执行的操作，仅接收执行结果、摘要和主机额外的 AI/速度状态。观众仍收到完整成功操作。三个真实对局中，客端完成帧的重复游戏操作计数均为零。主机上传给中转的完成帧仍完整，云端不保存整份指令队列来重建观战数据。
- **编队移动批量传输。** 一个 `command_batch` 最多 64 条，超过时拆分；每单位的位置、行军速度、序号和校验均保留。UI 移动和阵型切换直接使用批量入口，单人行为不变。一个包含 50 个单位、各自目标和共同速度的 JSON 样例，从 50 条共 6572 字节降为一条 3159 字节，减少约 52%（仅这个上行指令样例，不是整局带宽）。每执行帧的 62 条容量与逐条接受/拒绝规则仍生效。
- **全量关键帧压缩。** Godot 对原有全精度 JSON 状态做 zlib 压缩，Base64 后仍走 JSON WebSocket。Python 有界解压校验格式后按压缩形式转发；客户端解压后走原状态摘要和恢复路径。展开上限 4 MiB，拒绝截断、多余数据、错误长度、异常 JSON 及非法 Base64。

真实传输大小已包含压缩封装和 Base64 开销（不含 WebSocket/TCP/TLS）：

| 地图 | 原始状态 JSON | 压缩关键帧报文 | 缩减 |
| --- | ---: | ---: | ---: |
| 小地图 | 228–233 KB | 7.4–9.5 KB | 约 96% |
| 默认地图 | 546–547 KB | 48.3–48.7 KB | 约 91% |

默认地图一次快照从约 0.55 MB 降到约 49 KB，明显降低开局、观战加入和失步恢复的带宽突发。这是初始/短局地图状态测量；长局实体、路径等内容不同，压缩比例也会变化。

第二阶段主要针对大包与密集操作。少量操作的持续出口仍约 6.6–6.8 KB/s，接近第一阶段，不能将快照的 91% 压缩率理解成整局带宽下降 91%。100ms 输入预算、游戏速度和执行摘要频率不变。

验证：Python 服务 160 项；Godot 调度 116 项、协议/压缩 72 项、编队/UI 118 项、语音反馈 18 项通过。UI 测试中原有右键坐标断言未考虑 1/1024 定点量化，在改动前同样失败，已改为核对量化后的目标。三个真实对局覆盖低延迟、人工抖动、默认地图、交换主机、观战加入和主动失步恢复；最终摘要一致，无额外自然失步，直线回退为零。2 倍速稳态约 59.6–60.6 ticks/s，时间线差 P95 28–32ms。

记录：`.godot/online-fair-e2e-l856yxv2`、`.godot/online-fair-e2e-m5orwcy1`、`.godot/online-fair-e2e-ben2cowu`。服务端字节统计位于 `traffic-summary.json`，游戏回归里的 `keyframe_bytes` 仍是解码后调试表示的大小，不应作为压缩后的网络流量。

**客户端、观众和中转需要一起升级到 v8；v7 及以前拒绝匹配。** AI Python 配置不变。本轮没有部署云端或提交 Git。

## v6 公平调度流量排查（2026-11-16，优化前基线）

结论：公平调度增加了正常的持续消息开销；删除本地预测只删除表现代码，不会减少这些协议报文。用户报告的云端约 200 kbps 相当于 25 KB/s。它不能直接与历史文档的单向 `frame` 数据相比较：历史 1.3 KB/s 只算 1 倍速完成帧，未计 ACK、准备/提交、玩家输入、观战和传输层开销。

### 实测口径与结果

通过测试专用 ASGI 包装器统计中转入口/出口实际 JSON 文本的 UTF-8 字节数。生产游戏和服务不改动。默认 2 倍速，双玩家加一个晚加入观众，少量人工指令，未启用 LLM；测量稳定 tick 300–435（约 2.3 秒、45 个完成帧），单独列出关键帧。统计不含 WebSocket/TCP/TLS 头、压缩、重传、HTTP 或其他服务流量，因此不是网卡抓包值。

| 服务端方向/范围 | 小地图、无附加网络延迟 | 默认地图、每代理方向 25ms + 0–10ms 抖动 |
| --- | ---: | ---: |
| 发给两位玩家合计 | 9.47 KB/s ≈ 75.8 kbps | 8.76 KB/s ≈ 70.1 kbps |
| 两位玩家上传合计 | 9.06 KB/s ≈ 72.5 kbps | 8.38 KB/s ≈ 67.1 kbps |
| 额外发给一名观众 | 2.74 KB/s ≈ 21.9 kbps | 2.55 KB/s ≈ 20.4 kbps |
| 出口合计（含观众） | 12.21 KB/s ≈ 97.7 kbps | 11.31 KB/s ≈ 90.5 kbps |

小地图实测出口按消息类型拆分（两位玩家，未加观众）：

| 消息 | 用途 | 约 KB/s |
| --- | --- | ---: |
| `frame` | 完成指令、结果与摘要 | 2.74 |
| `ack` | 客端执行确认 | 2.23 |
| `input_frame` | 提前发布有序指令，空帧也发送 | 1.00 |
| `input_commit` | 共同执行时刻、速度与输入预算 | 2.29 |
| `input_ack` | 已接收准备帧的累计确认 | 0.83 |
| 时钟探测/回复及少量操作 | 对齐时钟、转发客端指令 | 0.38 |

旧实现（`e4d2d69`）每网络帧是 `frame + ack`，当前是 `input_frame + input_commit + frame + input_ack + ack`。相同 2 倍速每秒约 20 网络帧，对应双方合计约 40 → 100 条持续报文/秒，另加时钟和操作。从当前报文的组成估算，新增准备/提交/确认和时钟约占一半基础出口字节；这不是旧版本同条件实跑的精确倍率。旧完成帧还没有当前 `results` 字段。

代码入口：`scripts/network/fair_lockstep.gd` 的 `_prepare`、`_commit`、`_ack_plans`、`poll`、`_finish`；云端 `multiplayer_service_python/matchmaking.py` 转发这些消息。

### 其他会增加带宽的因素

- **真实推进速度恢复。** 此前网络等待使 2 倍速只跑约 19–45 ticks/s，修复后接近 60；每现实秒的消息数相应恢复。不能拿慢速故障时的低带宽作为正常基线。
- **指令重复携带。** 成功操作先在 `input_frame` 发布，随后在 `frame` 再发一次，客端和观众都收到完成帧；编队逐单位下令和 AI 操作密集时，这部分比空闲测试更大。客端下令还先经过一次 `command` 转发。
- **小消息的封装成本。** 空 `input_frame` 约 47–50 字节，`input_commit` 约 115 字节，均独立调用发送；实际 TCP 分段、确认、是否使用 TLS/压缩会改变网卡流量，消息数不能简单等同于 TCP 包数。
- **观战。** 每名观众持续接收一份完成帧，并在加入时接收一次完整世界。准备帧、提交与时钟消息只在两位玩家之间转发。
- **关键帧突发。** 默认地图每份实测约 0.547 MB；小地图约 0.23 MB。一次默认地图快照摊在一分钟指标里也约增加 73 kbps（未计压缩），摊在更短窗口里峰值更高。它用于开局、观战加入和失步恢复，不是每个网络帧发送。

稳定窗口中两组测试的重复 `input_frame`/`input_commit` 均为零，未出现自然失步。整局各发送三份关键帧，分别用于客端开局、观众加入、测试主动注入的一次失步；请求可能因房间限频等待后重试，不会每次请求都发送完整世界。恢复时会重发未完成的准备帧与提交，是有界行为。

**对 200 kbps 的判断：** 若监控显示进出合计，双玩家 JSON 已约 137–148 kbps，加观战或封装后接近 200 并不奇怪；若是纯出网、无观战、无大量操作且长期稳定 200，则高于本次空闲基线，尚不能仅凭该数值确定全部来源，需要同一时间窗口的消息统计或服务器流量记录。此测量没有连接用户云端，也不涵盖同机 LLM/HTTP、其他房间和公网重传。

### 可减少开销的顺序

1. 稳定阶段把准备内容与执行时间合并发送，保留开局校准和共同未来帧规则，不为了凑批次增加输入等待。
2. 减少稳定期逐帧 `input_ack`，改为周期累计确认；保留开局及恢复所需确认。当前时钟回复也会触发同一准备 tick 的再次确认。
3. 面向玩家的完成确认仅携带 tick、结果与摘要，观众仍接收完整操作，避免成功指令在客端收两遍；需要客户端和服务协议配套修改。
4. 速度、输入预算等固定字段仅在初始化/变化/恢复时发送。先测收益，再考虑二进制编码或压缩。

## 协议 v3 的增量操作帧实测

主机不再每秒发送 10 份完整世界。每帧只有有序操作、tick 和 SHA-256 摘要；空帧仍推进模拟。双方每帧运行三个 `1/30` 秒固定步，步在物理帧中逐个执行；主机最多领先客端确认 6 帧，观众独立跟随。

本机三进程回归（默认地图，队伍 2 为主机，453 tick）中，客端收到 151 个操作帧，共 18,934 字节，平均约 **125 字节/帧**。按目标 10 帧/秒计，操作帧约 **1.3 KB/s**，另有 ACK、玩家输入、心跳及 WebSocket/TCP 开销。这里的操作负载较轻；大量选中单位、连续下令时会增加。

该次观众中途加入的完整关键帧约 **0.54 MB**，只发送一次。客端额外注入一次资源错误，收到第二个关键帧修复，之后重新稳定使用增量帧。三个进程最终 tick 与摘要一致。关键帧保存精确浮点位模式，防止跨 JSON 实现的微小舍入造成假失步。

降低网络流量不等于免除模拟成本：双方及每个观众都需要运行完整游戏逻辑，并生成校验摘要。帧以 6 帧窗口流水线推进，往返延迟加客端缓冲超过 0.6 秒才会降低游戏速度；没有客户端预测，客端操作的生效延迟约为往返延迟加 1–2 帧。寻路使用固定请求数量预算，不能因设备快慢而改变模拟顺序。

复现入口：

```powershell
python tools/test_incremental_e2e.py --godot "<Godot console executable>"
python tools/test_incremental_e2e.py --godot "<Godot console executable>" --default-map --host-team 1
Godot_console.exe --headless --path . --script res://tests/bench_lockstep_frame.gd -- 60 40
python tools/bench_lockstep_e2e.py --godot "<Godot console executable>" --army 30 --seconds 20
```

输出包含每个进程的 tick、摘要、操作帧流量、关键帧数量和失步次数；临时日志在 `.godot/incremental-e2e-*`。测试主动注入的那一次客端失步是预期行为，额外失步会使测试失败。

## 增量同步卡顿排查（signal_simple）

改为 v3 后联机明显卡顿，原因有四个，彼此叠加：

1. **串行确认屏障。** 主机必须等客端确认上一帧才开始下一帧，而客端收到帧才开始计算。每帧耗时 = 主机计算 + 中转 + 客端计算 + 中转，两台机器轮流空等。有往返延迟时更明显。
2. **集中执行。** 一个渲染帧里连续跑 3 步、全量校验和 3 次迷雾刷新，每 100 ms 卡一次；单位位置也只按 10 Hz 跳变，没有插值。
3. **每帧全量校验。** 每帧把整个模拟状态（含约 1000 棵树、路径、迷雾）转换成 Variant、排序字典、序列化成约 0.58 MB JSON 再做 SHA-256，耗时超过一个模拟步。
4. **每步固定开销。** 每步扫描所有约 1200 个实体子节点 4 次做编号和排序；迷雾的纹理、记忆和节点显隐（纯表现）每步刷新 3 次，单机只需 10 Hz。

对应修改：

- 帧流水线：主机按实际时间产出帧，按 tick 保存已发布摘要，确认异步到达，领先窗口 6 帧。客端缓存帧，1 帧抖动缓冲，积压时追赶。关键帧请求在帧边界回答。
- 每个物理帧执行 1 步（主机最多 2、客端追赶时最多 4），每渲染帧最多 2 × 速度 步。对局速度取主机的 `[game] speed` 并在帧内广播（v3 原实现按 1 倍实际时间推进，比单机默认 2 倍速慢一半）。
- 每帧摘要改为二进制紧凑摘要（`LockstepState.digest`）；每个整模拟秒的帧改用完整摘要（`LockstepState.full_digest`，见下节）。原 JSON 形式的 `checksum()` 保留给关键帧往返测试。
- 新增实体按 `child_entered_tree` 增量编号，单位/建筑/箭矢的 net_id 顺序缓存；迷雾每步只重建可见栅格，表现层在渲染帧按 10 Hz 刷新。
- 结果不变的热点优化：空间哈希对单位直接读取定点坐标、按 net_id 用原生整数排序；`units_in_radius` 使用类型化字段；路径点可见性检测内联定点运算（2 万条随机线段与原实现逐一比较一致，快 3.4 倍）。
- 中转服务：每处理一条消息让出一次事件循环，默认输出队列由 8 提高到 64。玩家对 30 个单位一次下令就是 30 条指令连续转给主机，旧设置下可能因 `slow_consumer` 断开主机。

下表为 1 倍速测量；2 倍速需要每秒 60 个模拟步，CPU 需求翻倍。同一 2 核虚拟机、两个客户端同机时，默认地图加每方 5 / 15 个士兵分别达到 1.35× / 1.17×（目标 2×），瓶颈是 CPU。

验证结果：同一场景下，修改前后跑 129 tick 的完整状态哈希完全一致（`bench_lockstep_frame.gd` 输出 `deep state`），说明模拟结果没有改变。下列数字来自 2 核云端 Linux 虚拟机，headless，主机、客端和中转同在一台机器，只用于相对比较。

| --- | --- | --- |
| 每网络帧（3 步 + 校验） | 293–305 ms | 136 ms，另有约 12 ms 迷雾表现（渲染帧，10 Hz） |
| 单个模拟步 | 79 ms | 43 ms |
| 每帧校验 | 55 ms | 4.8 ms |

| --- | --- | --- |
| N=10，本机回环 | 0.30×，每帧 170–240 ms 卡顿 | 0.97×，99% 帧 ≤ 71 ms，最差约 110 ms |
| N=10，往返延迟 120 ms | 0.23×，卡顿 145–220 ms | 0.96×，99% 帧 ≤ 81 ms |
| N=5，往返延迟 120 ms + 0–80 ms 抖动 | — | 0.99×，客端仅 1% 物理帧等待 |
| N=30，本机回环 | 0.15×，卡顿 280–440 ms | 0.63×（两进程同机，CPU 已饱和） |

上述优化后，剩余主要开销是单位移动本身：局部避让、邻居查询和路径点可见性检测约占模拟步的七成，单机同样存在，联机时双方都要计算。机器跟不上实时时，对局会整体减速，而不是周期性冻结。

2026-10-31：这三处改为整数运算的 C++ 扩展，求解得到的方向最多沿用 0.25 秒。同时修正了 `bench_lockstep_frame.gd`：它原先用主机身份给双方下令，另一方的指令被拒绝，上表实际只有一方在移动。按修正后的基准（双方各 60 个单位都移动），单个模拟步由 63.5 ms 降到 20.3 ms，每网络帧由 199 ms 降到 67 ms；每方再加 20 名士兵、目标 2 倍速的双进程对战由 0.82～1.04× 提高到 1.28～1.45×。原生模拟步的剩余开销主要是实体逻辑（约 14 ms，其中避让求解约 1.4 ms）和迷雾栅格（约 5 ms）。实现、确定性验证和构建方法见[原生模拟内核](native_simulation.md)。

2026-11-01：迷雾栅格也改为原生计算，锁步模拟步内的精灵绘制延后到渲染帧，单位缓存服务节点。同一基准每步约 21.8 ms → 14.6 ms，模拟结果不变；双进程对战的渲染帧间隔中位数从约 60～70 ms 降到 13～28 ms。

### 紧凑摘要与完整摘要

紧凑摘要只哈希主要玩法数值，护甲、建筑接收资源的设置、城门导航记录等隐藏字段不在其中。`tests/run_lockstep_digest.gd` 对默认地图上一个运动中的局面逐个修改 357 处同步状态，原 JSON 校验能发现其中 355 处，紧凑摘要漏掉 94 处。这类差异要等到影响某个被哈希的数值时才会暴露，可能已过去很久。

因此 `frame_checksum()` 按 tick 选择摘要：帧结束 tick 是 30 的倍数（每个整模拟秒，即每 10 个 3-tick 帧）时使用完整摘要，其余帧使用紧凑摘要。选择只取决于 tick，主机、客端、观众以及帧、确认和关键帧对同一 tick 总是用同一种摘要；任何隐藏状态的分歧最迟在 1 个模拟秒内被发现，随即用关键帧修复。

完整摘要覆盖 `capture()` 的全部状态，取值规则与之相同（引用转为网络 ID、字典按键排序、`Vector2` 分量不区分正负零），直接对二进制形式（`var_to_bytes`）做 SHA-256，不组装关键帧字典，也不生成 JSON。同一测试中，完整摘要对 357 处改动的判定与原 JSON 校验完全一致；人为让它保留 `Vector2` 零的符号、漏掉迷雾、漏掉地面支撑、把弱引用一律记为 0、不排序字典或少算一个字段时，测试分别报告分歧。

| 摘要 | 默认地图 | 27 分钟存档（1446 个同步实体） |
| --- | ---: | ---: |
| 原 JSON 校验 | 27 ms | 75～90 ms |
| 完整摘要 | 11 ms | 25～31 ms |
| 紧凑摘要 | 3 ms | 7～8 ms |

`bench_lockstep_frame.gd -- 60 60` 中每帧校验的中位数不变（约 4.3 ms），每 10 帧一次的完整摘要帧最长 24～28 ms，摊到每帧约 2 ms。

摘要的计算方式改变后，与之前的客户端即使协议版本相同也不能混用，否则会持续判定失步。

## 历史 v1 问题

旧版使用完整 JSON 快照，静态资源、实体和迷雾反复发送，默认场景约 195 KB/帧，正常 10 Hz 时约 1.87 MB/s。旧实现还曾按游戏倍速增加发送频率，引发收发队列积压；复现中的断开原因为 `slow_consumer`。后续 v1 修复将网络频率改为实际时间并合并过时快照。

v3 保留实际时间超时、消息大小限制和连接诊断，但不再合并增量帧。日志中的 `slow_consumer`、`rate_limited`、`send_timeout` 或 `idle_timeout` 分别对应输出积压、输入限流、发送超时与心跳超时。旧 `tools/test_network_stability.py` 和周期快照测试针对 v1，不能作为当前协议的性能断言。
