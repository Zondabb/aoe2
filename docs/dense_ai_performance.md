# 多单位、城墙与 AI 场景性能优化

本轮针对双方基地、多村民和军队、完整城墙、内置 AI，以及周期性完整 AI 观测同时运行的场景。目标是在保留采集、建造、战斗、碰撞与视野规则的前提下，减少重复计算和单帧工作堆积，并用实际 GPU 渲染基准检验接近 60 FPS 的程度。

69 单位、216 墙并每模拟秒构建完整观测的场景，平均帧率从 31.4 提升到 55.7 FPS；同规模施工场景达到 64.1 FPS，接近 60 左右的目标。89 单位、432 墙的完整观测重场景仍为 44.3 FPS，尚未达到稳定 60 FPS，不能宣称所有规模均已达标。完整原始统计、日志路径和测试概要保存在 [dense_ai_performance_results.json](dense_ai_performance_results.json)。

## 已消除的重复工作

### 单位、碰撞与寻路

- **单位邻居索引**：移动避让使用独立的单位空间索引，不再先查询附近大量城墙和建筑再逐个筛除。单位注册、移动、死亡、删除和定义变化同步维护索引，返回顺序与原索引筛选结果保持一致。
- **避让候选计算**：将候选循环中的邻居字典改为强类型快照，预计算半径平方和接触间隙。超出“双方半径、预测余量与最大相对移动距离”之和的邻居，不可能与任一候选速度发生本步或预测期接触，可以安全剔除。保留其余邻居的顺序、候选顺序与评分。
- **半径层延迟同步**：不同兵种的通行半径仍各自使用准确的净空层。只读通行检测、建造位置检测和缓存路径查询不再反复将整层障碍同步到 A*；实际搜索前再同步。
- **不可达路径缓存**：封闭城墙内外的相同静态起终格不再重复进行失败的全图搜索。空路径使用原有的有界缓存，几何变化与手工网格修改都会使其失效；临时人群障碍产生的路径不写入静态缓存。
- **视线采样内联**：路径拐点的可见性检测保持原来的采样数量、位置和顺序，直接计算格索引并读取障碍字节，减少每个采样点的方法调用。
- **外观与城门**：相同动画帧的热点偏移和队伍颜色结果直接复用；城门只检查单位组中的同父级单位，避免遍历全部树木、资源和墙体。

这些改动以保持查询和判定结果为目标。随机风险对照、射线对照和空间索引生命周期测试用于检查这一点。

### AI、迷雾与地图信息

- 内置防御管理器使用专用的简化观测，只计算墙体规划和可见敌方位置，省去此调用不消费的生产、研究、普通建造候选与探索前沿数据。完整 Gateway 观测继续提供完整协议字段。
- 同一次完整观测内复用相同建筑、文明、队伍和比赛状态的可训练单位列表；资源不足、队列和研究阻塞原因仍按建筑实时读取。
- AI 观测、黑板和小地图在几何与迷雾版本匹配时复用静态实体可见性。移动、队伍变化、新实体和迷雾版本变化保留实时回退。
- 城墙防御规划先排除不可能与候选墙线相交的远处障碍；已齐备的墙段批次跳过不再需要的放置可见性检查。
- 探索前沿只缓存与探索掩码及地图几何有关的部分；当前侦察单位位置、阻挡和路线仍实时计算。保存探索掩码时使用独立副本，确保原地探索更新能使缓存失效。
- 迷雾将静态建筑视野圆的并集缓存下来，移动单位仍按本次位置盖章。位置、视野半径、队伍和生死变化通过值签名触发重算。
- 静态迷雾记录改为强类型对象，并用队伍位标记可见和已观测状态，减少每次重建的大量字典写入。实体列表改变时重建 ID 索引并使可见性缓存失效；已观测几何与当前几何分别保存，外部几何刷新不会误用旧的可见性结果。

## 计算调度的变化

以下调度会改变计算发生的时机，不能与严格等价的缓存优化混为一谈。

### 30Hz 物理与渲染插值

默认物理更新频率由 60Hz 改为 30Hz，并启用物理插值。**30Hz 不限制渲染帧率**：显示仍可以每秒渲染约 60 帧，插值补齐两个物理状态之间的显示位置。

默认游戏速度为 2 倍时，旧配置每个物理 tick 推进 `2 / 60 = 1/30` 模拟秒，新配置每 tick 推进 `2 / 30 = 1/15` 模拟秒。每秒推进的模拟时间仍为 2 秒，计算步长变大、物理调用次数减半。

单位出生时重置插值历史，避免从场景原点滑入；远端复制实体使用自身的网络呈现更新。遮挡轮廓需要使用与主体一致的插值平移，避免主体与轮廓错位。停滞帧计数按物理频率折算，默认 30Hz 每步累计 2 个原 60Hz 计数，保留 AI 原有的实际时间阈值；以 `delta` 计时的停滞恢复继续使用模拟时间。

采集、攻击和生产等跨 tick 事件存在步长量化差异。例如到达采集位置或交付资源的事件可能在相邻物理步确认，因此相同模拟时长的短样本不保证资源数量逐项完全相同。针对采集跨 tick 量化差异的 **117 项检查**用于验证可接受的边界及继续采集行为；不能将量化差异描述为逐 tick 完全一致。

### 拥挤场景的转向复用

附近至少有 12 个单位时，为每个单位保留约 0.1 模拟秒内的转向选择，并错开首次刷新。其间每个物理步仍根据当前邻居重新检查扫掠碰撞和预测接触，同时检查当前静态障碍、前方预测段及地图边界；不缓存邻居位置或障碍几何。

目标改变、明显转向或变速、位置突变、新障碍、风险升高和停滞会立即重新求解。原来的直接期望速度重新变得安全时，也立即采用它。小规模场景继续使用原求解流程。该调度允许拥挤单位的短时轨迹与每步完整评分产生差异，但不允许借助旧速度穿墙或产生新的单位重叠。

寻路队列同时保留每帧最多 12 条请求的上限，并增加约 2ms 的实际时间预算；每帧至少处理一条，后续请求按原顺序继续。**单条 A* 搜索不可中断**，因此 2ms 是请求之间的让出预算，并非单条搜索或整帧耗时的硬上限。

### Gateway 观测与规划分帧

真实 Gateway 使用 `Observation.build_budgeted()` 和 `DecisionContext.build_budgeted()`，以软 4ms 预算在主线程分帧准备观测。实体收集循环及目录、导航、军队、防御、建造与侦察规划之间设置让出点；暂停前后清理失效、待删除节点，并检查实体容器是否仍在场景中。只有完整准备完成后才发送请求，取消时不会发送半成品。

原 `build()` 和同步调用方式保留，旧测试、内置调用及未选择预算接口的调用方仍立即得到 `Dictionary`。冻结场景下，同步与预算接口的 JSON 字节一致；运行中的预算采样会跨越多个渲染窗口和模拟步，因此高层观测允许包含近实时组合状态，不能视为同一瞬间的原子快照。请求时间戳统一使用开始捕获时的时间，避免准备期间的耗时使观测、封装与事件时间互相错位。

取消 generation、手动控制 fence 与执行器的最终命令验证继续生效。分帧期间发生控制权切换、退出或场景销毁时，旧请求不能越过这些检查执行；空观测不会确认尚未发送的事件。分帧减少单次主线程集中工作，也可能增加一次请求从开始采样到发出的总延迟。

**4ms 是检查点之间的软预算，不是单帧硬上限**。单个 `_catalog`、防御、建造或侦察阶段内部仍不可抢占，耗时较长时要等该阶段完成才让出。预算调度也不暂停世界中的采集、建造和战斗。

### 大型 HTTP 请求的 JSON 编码

较大的纯数据请求先在主线程检查所有键和值，拒绝循环容器和过深嵌套，再用原生深复制冻结可变容器；后台任务只持有独立的纯数据 `RefCounted` job，执行协议值转换和 `JSON.stringify()`，不访问客户端 Node 或场景 Resource。主线程仍承担验证和冻结成本，完成编码后回收任务，再按原运输队列发送。

小请求、包含 Object、Callable、Signal、RID 或 packed 数组等不适合直接跨线程冻结的数据，以及 Web 导出，继续使用原同步路径。纯数据后台编码与原编码器的输出字节保持一致。取消和树退出会回收任务，并在客户端销毁前唤醒已有等待者；旧 generation 的等待者不能清除新请求的任务槽。编码中的原生操作不可中断，取消清理可能等待当前任务完成。

## 复现性能测量

在同一台机器上顺序运行对照版本，使用同样的地图、单位数量、游戏速度、窗口尺寸和采样帧数。以下 PowerShell 示例中的引擎路径应替换为本机实际路径。

```powershell
$denseGodot = 'E:\Program Files\Godot_v4.7.2-stable_win64.exe\Godot_v4.7.2-stable_win64_console.exe'
& $denseGodot --path . --fixed-fps 60 --resolution 1280x720 `
  --script res://tests/benchmark_walls.gd -- `
  --scenario walls --villagers 40 --military 40 --both-bases --ai `
  --samples 600 --observation-interval 1.0
```

这个命令对应表中的 89 单位、432 墙完整观测重场景，保留本机 GPU 实际渲染，覆盖双方基地、村民和军队、城墙、内置 AI 以及每 1.0 模拟秒一次的完整观测压力。当前版本会选择预算观测接口，并调用真实 HTTP 客户端的独立编码方法；此压力测试不发送网络请求，也不调用付费服务。已有观测尚未准备完成时不叠加另一份准备任务。

基准默认使用软 4ms 观测预算；添加 `--sync-observation` 可单独比较同版本的同步观测准备。实际 Gateway 使用相同预算入口，但另有请求响应、取消、控制权和事件交付状态检查，不能仅用独立准备基准代替 Gateway 生命周期验证。

`--fixed-fps 60` 固定模拟帧推进，实际耗时仍需由基准记录；它本身不证明已经达到 60 FPS。报告应列出实际单位和城墙数量、物理频率、游戏速度、分辨率、平均帧时、P95/P99、最长帧与超过目标帧时的帧数。观测还应区分各主线程工作片段耗时与从开始采样到编码完成的总延迟；后者会包含主动让出的渲染窗口。

加入 `--headless` 可以单独比较 CPU 工作量，但该模式不承担实际窗口渲染和 GPU 成本，其结果只作为 CPU 对照，不能单独充当游戏 FPS 的证据。性能测量期间不并行启动其他基准或测试，避免相互争用导致误判。

## 尚存限制

真实 Gateway 的完整观测和上下文已在主线程按阶段分帧，大型纯数据 HTTP 请求的协议转换与 JSON 编码已转交后台。观测验证、请求冻结和各规划阶段内部仍有不可抢占工作；旧同步 API、内置调用以及 JSON 回退路径也继续同步执行。因此周期性观测仍可能造成帧时尖峰，软 4ms 预算不能作为每帧最大耗时承诺。单条复杂 A* 同样可能突破队列的 2ms 预算。

分帧窗口越多，请求快照的总准备延迟可能越长；运行中的输入也可能跨越数个模拟步。取消 generation、手动控制 fence 和执行器验证保证旧决策不能绕过现有控制权及合法性检查，但不保证高层 AI 看到严格同一时刻的世界。后续优化需要同时衡量帧时分布、准备延迟与实际行为，避免仅将卡顿转化为过长的决策等待。

接近 60 FPS 的结果仅适用于本次硬件、分辨率、地图密度与观测频率。69 单位、216 墙场景平均约 56～64 FPS，但 P99 仍超过 40ms；89 单位、432 墙并周期性完整观测仍为 44.3 FPS，整体尚未达到稳定 60 FPS。表中同时保留平均帧率和长帧分布，避免以平均值掩盖 AI tick 或集中建造时的卡顿。
